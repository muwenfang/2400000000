## 需求2：商店祝福随机性排查
数据源是 `prefabs/Library/BlessingLibrary.asset` 的 `allBlessings` 引用列表（代码 BlessingLibrary.cs 是死代码）。共 70 个祝福资产。查出 3 个问题：
1. **两个祝福根本没被库引用 → 永远不会出现在商店**：`3纯粹容器`（guid 8e0564e6…）、`14好事成双`（guid 73ee5ff3…）。已把这两条 append 到 BlessingLibrary.asset。
2. **blessingId 重复**：`68反物质核` 与 `69缤纷多彩` 都是 id=68（且 id 69 空缺）。id 重复会让 `HasBlessingEverBeenPurchased`/`GetBlessingCount`/`RemoveBlessingFromPool(按id)` 互相串味，缤纷多彩（NeverRefresh）一旦反物质核被买过就被判「已购」而永不再现。已把 `69缤纷多彩.asset` 的 blessingId 改为 69。
3. **`RemoveDisplayedBlessingsFromPool` 是空操作**：`GenerateBlessings()` 第一行就 `shopBlessings.Clear()`，之后才调用该函数，列表已空 → 刷新时可以立刻重复刷出同一批祝福。已改为在 Clear 前快照 `previouslyDisplayed`，并把剔除调用移到最后、加「剔除后仍 ≥ neededSlots 才生效」的安全保护（避免可选祝福稀少时空槽位）。
- 结论：blessingType 全部唯一且与枚举一致，无权重字段，抽取本身是均匀的。
- 验证：`D:\unity\hc_check` 编译 0 错误；回归 82 → **87 项全过**（新增 5 项覆盖剔除+保护）。

## harness 新发现（重要）
- 离线 `UnityEngine.Object.operator==` 对「两个非空对象」比较的是 **`m_InstanceID`** 而非引用（`m_CachedPtr` 只管判空）。`GetUninitializedObject` 出来的实例全是 0，导致任意两个假对象 `==` 恒为 true → 被测代码里「按实例剔除/去重」的分支会一次删光整池。造互相比较的假对象时必须给**各不相同的非 0 `m_InstanceID`**。已写入 `unity-offline-verify` 技能。
