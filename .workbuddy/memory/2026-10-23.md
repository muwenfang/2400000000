## AlwaysRefresh 祝福权重：时序核查 + 锁定槽位统计修复
- 用户反馈"概率感觉不对，怀疑每回合进入商店时权重被重置"。核查结论：**时序本身没问题**——`OpenShop`（每回合进商店，GameManager.EndTurn 里调一次）→ `GenerateBlessings()` 末尾 `UpdateAlwaysRefreshAppearanceTracking()`；`ResetAlwaysRefreshTracking()` 只在 `InitializeShop()`（普通/内卷开局）。场景里没有 `InitializeShop`/`InitializeGame` 的 UnityEvent 绑定，也没有任何 `LoadScene`，所以运行期不会重建 ShopManager。
- **真正的 bug（已修）**：`shopBlessings` 恒填满 `MaxBlessingCardCount`(4) 个槽位，其中 `index >= blessingCardCount` 的是锁定槽位（玩家看不到、买不到，仅用于解锁后直接显示）。旧统计把它们算作"出现"，导致祝福被抽进锁定槽位时连击被白清零 → 保底攒不起来。改为只统计 `index < blessingCardCount`（`blessingCardCount<=0` 异常态不裁剪，保持旧行为）。模拟：最坏可见间隔 115 → 68 个商店。
- 顺手修：`EnterEndlessMode()`（无尽模式开局）原不重置统计，会继承上一局的连击；已加 `ResetAlwaysRefreshTracking()`。
- 代码默认值对齐场景：`alwaysRefreshPityThreshold` 3→8、`alwaysRefreshPityWeightPerMiss` 10→1（场景 YAML 本就是 8/1，运行期行为不变，仅避免新建实例走错默认）。
- 新增排查开关 `logAlwaysRefreshTracking`（默认 false）：每次生成商店打一条摘要（第 N 次生成 / 可见槽位 / 已加权个数 / 最高权重祝福及其连击）。
- 体感偏弱的量化原因：34 个 AlwaysRefresh 同步累积、加权互相稀释；2 个可见槽位时单个祝福中位间隔约 19 个商店，streak 8/10/16 的单次抽中率仅 6.6%/12.4%/27.8%（基准 3.6%）。
- 校验：hc_check 新增 13 项（锁定槽位语义、跨回合累加、权重提升、源码守卫：重置只允许在 InitializeShop + EnterEndlessMode），回归 **196 项全过**。

## 祸星：只在"刚进商店"那一次可能出现的逻辑修复
- 现状 bug：`OpenShop()` 在 `GenerateBlessings()` **之前**调 `MarkDisasterStarExcluded()`（且外面还套了 `if (refreshCount > 0)`）——`refreshCount` 是跨回合累计值，玩家刷过一次后就恒 >0，于是祸星每回合首次生成前就被排除 → 整局完全不出现。
- 修复：把 `MarkDisasterStarExcluded()` 移到 `GenerateBlessings()` **之后**，去掉 `refreshCount` 判断。语义：OpenShop 首次生成时祸星仍可能被抽中；生成完立刻进排除列表，本回合 RefreshShop / FreeRefreshShop 不再出现。排除列表每次 OpenShop 开头 `Clear()`，所以每回合都重新给一次机会。
- 权重统计配合：`UpdateAlwaysRefreshAppearanceTracking()` 里对「已排除且本次未出现」的祝福 `continue`（不计连击）；若被暗箱操作强塞进可见槽位则仍按「出现」清零。效果 = 祸星每回合最多 +1 权重，刷新多少次都不变。
- 校验：hc_check 新增 `TestDisasterStarExclusion()`（12 项：首次生成计入、生成后进排除、刷新 3 次不再累计、未排除者照常累计、暗箱强塞仍算出现、源码守卫「先生成再排除」「不得用 refreshCount」「刷新路径不添加/不清空排除」），回归 **208 项全过**。
- 备注：`alwaysRefreshPityThreshold` 代码默认值现为 6（场景序列化为 8，运行期以场景为准）；`logAlwaysRefreshTracking` 尚未序列化进场景，Unity 下次保存场景时会自动补 false。
